# SlideForge 架构梳理与 1 万用户准备方案

> 日期：2026-11-01。这里的“1 万用户”按 **1 万注册用户** 理解，不等于 1 万并发生成。P0 架构收敛与 legacy 退役已完成；Go／Python 服务和各自存储按总纲继续推进。

## 1. 当前系统边界

SlideForge 当前只以独立交付服务作为现役主链路：CLI、MCP、HTTP 共用 `src/contracts` 与 `src/capabilities/deck.ts`，直接调用 OpenAI 兼容模型与 `ppt-engine`。

React／Host 旧体系已通过依赖可达性审计分批退役，共享模板资产继续保留。本轮 1 万用户改造只针对现役链路，不能把旧 React 工作台的 APS 能力当作独立 HTTP 服务已经具备的多租户能力。

```text
浏览器 / CLI / MCP 客户端
          │
          ▼
HTTP / MCP 入口（API key、用户隔离、限流、请求体上限）
          │
          ▼
有界重操作队列（生成、重生成、预览、换肤、导出）
          │
          ▼
src/capabilities/deck.ts
   ├── LLM：大纲与逐页 HTML
   ├── Chrome：确定性版面检查与缩略图
   └── ppt-engine：HTML → PPTX / PDF
          │
          ├── artifacts/decks：作品文件
          └── data：API key、任务快照、计费台账（单实例）
```

## 2. 原始瓶颈与本轮处理

| 风险 | 原始行为 | 本轮处理 |
|---|---|---|
| 请求打爆内存与 Chrome | 每个 POST 直接启动生成 | 全局有界队列，所有重操作共享容量名额 |
| 单用户或单 IP 滥用 | 无频率限制 | 通用分钟限流 + 创建任务小时限流 |
| 大请求体耗尽内存 | 全量读入且无上限 | 默认 32 MiB，超限 413 |
| 跨用户访问作品 | 仅创建和部分导出校验 key | deck / brand / MCP 全链路归属校验 |
| 重启丢任务 | 任务只在 Map | 原子 JSON 快照；重启后中断任务明确失败 |
| 并发扣费丢更新 | 整份 key 文件读改写 | 串行事务、原子替换、缓存副本隔离 |
| 任意路径写入 | HTTP 接受任意 `out_path` | 导出路径限制在当前 deck 工作区 |
| 生产裸奔 | 未配管理员 key 也全放行 | `NODE_ENV=production` 启动时强制管理员 token 和计费 key |
| 事件无限增长 | 每个任务持续追加 | 每任务最多保留最近 200 条 |

新增容量与运行参数见 `deploy/env.example`。`/healthz` 提供队列状态，`/admin/metrics` 提供进程内存和队列指标。

## 3. 当前能承诺什么

本轮完成的是 **单实例、受控灰度基线**，不是“1 万用户高并发已完成”。本地 JSON 持久化只适合单实例；没有跨实例锁、共享队列、对象存储和数据库事务。

建议首批生产配置从 4 核 8 GB、`DECK_JOB_CONCURRENCY=1`、`DECK_CONCURRENCY=2` 开始，根据压测逐步调整。该配置是容量起点，不是 SLA 承诺。

历史记录中 20 页 deck 约 70 秒，可作为估算参考但不能替代本轮压测。理论生成吞吐为：

```text
每小时任务数 ≈ DECK_JOB_CONCURRENCY × 3600 ÷ 单任务 P95 秒数
```

按 70 秒计算，1 路任务并发约 51 份/小时，2 路约 103 份/小时；还未扣除导出、预览和重生成占用的同一队列时间。因此要根据“高峰每小时创建多少份”而不是注册用户数扩容。

## 4. 上生产前必须完成

### 已完成的安全与可靠性改造

- API key 仅保存 SHA-256 哈希，旧明文文件自动迁移；哈希仅用于管理充值，不能作为认证凭证。
- REST 与 MCP 导出按用户、作品、格式、内容指纹幂等，支持 `Idempotency-Key`；并发或持久重试不重复扣费。
- 共享 Chrome 由进程统一管理，业务函数不再相互关闭浏览器，断连后自动重建。

### P0：发布阻断项

- 验证两个 API key 不能互查 deck、brand 和 MCP 资源；验证 413、429、503、重启恢复和导出路径拦截。
- 配置 HTTPS 反向代理、磁盘告警、`data/` 与 `artifacts/` 加密备份。
- 按产品要求跳过专项压测时，保持单实例与保守队列配置，不直接放大任务并发。

### P1：多实例与持续增长

```text
CDN / WAF / HTTPS LB
        │
        ▼
无状态 API 实例 ── PostgreSQL：用户、key 哈希、作品元数据、计费事务
        │
        ▼
Redis / 持久队列：生成、导出、预览分队列 + 公平调度 + 幂等键
        │
        ▼
独立 Worker + Chrome 池（按 CPU / 内存自动扩缩容）
        │
        ▼
S3 兼容对象存储：HTML、图片、PPTX、PDF
```

迁移顺序：先 PostgreSQL 与对象存储，再 Redis 队列和 Worker，最后 API 多实例。不要在仍使用本地 JSON / 本地作品目录时直接增加多个服务副本。

### P2：成本与可靠性

- 将生成、导出、预览拆成独立队列，避免导出被长生成任务饿死。
- 每用户并发与排队额度、全局公平调度、任务取消、超时与心跳。
- LLM 预算与熔断、按 `Retry-After` 退避、供应商配额监控。
- OpenTelemetry traces、结构化日志、Sentry、业务与资源告警。
- 作品保留策略与冷数据归档，避免磁盘无限增长。

## 5. 压测验收口径

至少覆盖 2 页、8 页、20 页三档，并按“创建 70% / 预览 15% / 导出 10% / 重生成 5%”做首轮混合模型；随后用真实产品数据修正比例。

发布门槛建议：错误率 < 1%、无跨用户数据泄漏、无持续内存增长、队列可恢复、P95 与等待时间符合产品目标。具体并发数字必须在压测后填写，不能预先宣称支持 1 万同时在线。

# 第五项：多人页面生成的技术设计

日期：2026-11-15。状态：已实施，验证范围及结果见[验收记录](验收记录.md)。产品约束以[PRD](PRD.md)为准。

## 1. 改造前代码事实（0b84b72）

- `src/capabilities/agent.ts:328–417`：一个worker包含提示词、模型、候选、静态校验、等待独立引擎校验及串行提交。当前`DECK_CONCURRENCY`默认2；初稿和批量修订共用该函数。
- `services/brain/brain/harness.py:223–275`：FIFO队列50、线程默认5，一个线程执行整个Harness任务，目前没有按客户的项目准入。
- `src/server/agentModel.ts`：页面调用共享Go预算与稳定调用ID；目前没有跨项目页面请求池，HTTP超时在实际发送时开始。
- `scripts/m0/llmClient.ts`同时服务页面、大纲和其他模型请求；Agent分支与固定流程分支不同，不能把所有调用一并记成页面请求。
- `src/capabilities/deck.ts:109`为固定流程页面模型调用点；`src/capabilities/agent.ts:395`为Harness页面调用点。HTTP与HTTP-MCP运行在同一业务Node；CLI及stdio MCP各自为独立进程。
- `ownerKeyHash`来源是业务访问Key的SHA256；在线鉴权和任务归属已有该字段，不从客户端新增自报owner。
- Go `jobs/budget.go`原子判断`spent + reserved + 本次预留`；当前没有区分暂时被在途占用和真正不足。
- Go `jobs/agent.go:111–130`当前只识别引擎等待与sent模型调用；增加容量等待后必须扩展计时依据，不能发现任意等待就给整项目停表。

## 2. 分层与部署边界

### Python：项目准入

沿用一个Brain实例和现有5个执行线程。待执行任务按业务Key分组，在有线程时轮转选择尚未达到每Key2个活跃项目的客户，客户内部按提交顺序选择。受限客户的队首不能挡住其他客户。

计数的获取、重复入队判断和释放在Runner同一锁内完成。所有返回和异常路径均释放名额；等待大纲/用户、预算暂停及结束不继续占线程。一个已有任务的重复enqueue不能重复占位或生成新执行身份。

沿用Go中的任务、epoch、租约、检查点与显式恢复规则，不因排队增加新的自动恢复或付费重发。入队失败仍保持原来可感知的错误及任务恢复边界。队列容量沿用50，不引入无限队列或新的外部基础设施。

本期“每Key2个Harness项目”指进入Python总控执行的任务。固定流程旧任务仍走已有任务队列，本期不迁移其项目准入；它们的页面模型请求共享下一层额度。

### Node：页面模型请求共享池

单个逻辑业务Node保存一个容量12的页面请求池，按owner轮转，owner内部按项目轮转、项目内部FIFO；没有竞争时立即派发，不固定切成每人小额度，不抢占已发请求。

在两个明确页面调用点传入用途、owner和项目身份，不按提示词内容猜测调用类型，不把大纲、品牌优化或Python总控误计入页面池。所有在线固定流程页面重试的每次实际请求同样需要取得槽位；既有退避等待不占槽，不增加重试次数。

槽位覆盖发送前的必要复核、预算预留及一次供应商请求，响应成功、失败或结果未知后均释放；解析后的引擎校验与项目提交不继续占页面模型槽。Harness自己的整页worker仍为3，不能为了填满12而越过整页工作位或放大引擎并发。

完成调用或子操作的已知成功回执直接复用，不排进供应商请求池，不重复预留或收费。槽位释放必须恰好一次；排队取消或执行失效不能漏占、重复释放或迟到发出请求。

共享池仅在当前业务Node内生效。独立CLI/stdio MCP、其他业务Node进程及Python总控不计入该池，不能宣称供应商整个账号被限制为12。以后客户端迁移Harness时，通过既有服务能力接入，而非各客户端另建Harness或另计额度。

### Go：预算、等待、取消与有效时间

Go继续独占金额和时间的权威状态。Node不能根据本地估算绕过reserve/send事务。内部错误保留可识别的机器码，不能通过中文报错字符串判断暂时不足，也不能把所有409或402都当可等待。

## 3. 一次Harness页面请求

1. 根据原操作ID和页ID恢复已有回执；分配一次稳定call_id和输入指纹。等待循环不递增调用计数、不换payload。
2. 记录本页当前本地工作状态。需要页面模型请求时进入共享池；此时尚未预留模型费用，也未启动供应商HTTP超时。
3. 获得槽位后重新读取Go执行状态，检查run_seq、epoch、取消、未知调用及已有回执。失效则退出并释放槽位，不能沿用排队前的旧状态发请求。
4. Go原子预留预算。真正不足或有效时间已满，停止新增派发并按现有语义暂停；暂时被在途占用，释放模型槽、记录预算等待，等待结算后重新排队。
5. Go原子确认send_call，随后发出一次供应商请求；reserve/send都必须拒绝当前执行中已存在的unknown，关闭仅靠Node先检查带来的竞争窗口。已经发出的其他调用不强行变成未发送。
6. 沿用原始响应落盘、usage结算、未知记录及恢复规则。请求结束释放容量；结算完成后唤醒或重新检查本项目的预算等待者。
7. 现有候选、方言、引擎校验、阻断范围和串行条件提交继续执行；排队调度不能改变已确认的页面内容或版本覆盖边界。

只有预算预留之前的等待检查可以再次尝试准入，这不是供应商模型重试。未知请求仍必须用户确认，不能由于释放了容量而自动重新发送。

## 4. 预算等待的判断

- `spent + 本次预留 > limit`：即使其他预留全部释放也不够，立即按现有预算不足处理。
- `spent + 本次预留 <= limit`，但加上当前reserved后超过limit，且有确实可推进、可结算的在途调用：返回独立的`budget_inflight`内部原因，等待结算后重新检查。
- 等待期间发生取消、epoch/run变化、unknown或真正不足，立即结束等待并按原语义交给调用方；不把未知调用当成普通等待。
- 有效时间已经耗尽，不能通过等待其他金额释放来绕过时间上限。
- 无可推进调用、状态已失效或等待检查本身失败时，直接报告错误并保留已有记录，不能无限静默等待。

共享费用仍使用原保守预留与实际usage结算，既不降低预留来凑并发，也不提高任务预算。Node/Python内部客户端按Go原因分类，HTTP层保留机器码；不增加供应商自动重试。

## 5. 纯等待与实际执行

复用现有sent调用、EngineWaits及epoch边界，并登记当前工具/页面的本地工作与资源等待状态。Go据此判断整个项目是否只有等待：

| 同一项目当前状态 | 有效时间 |
|---|---|
| 排队尚未获得Brain项目名额 | 不计 |
| 全部未结束页面仅等待模型容量/在途预算，且无实际工作 | 不计 |
| 仅等待引擎排队，无其他工作 | 不计 |
| 有一个模型已sent、引擎正在运行，或有本地生成/提交工作 | 按墙钟计一次 |
| 等待用户、预算暂停、取消或结束 | 沿用原phase规则 |

不能仅凭“有一个页面在等容量”停止整项目计时；也不能把三页并行时间累加三遍。登记状态应覆盖等待前后和finally清理；claim、新执行及终态清除旧等待状态，迟到旧epoch不能修改现执行的计时依据。

预算等待中若仍有其他模型执行，该段仍计有效时间；前端必须与此规则一致。内部轮询和心跳继续保活，排队时间不混入供应商240秒请求超时；真正网络/服务错误不吞掉。

## 6. 取消、故障和隔离

- 用户明确取消后，待发队列项立即撤销，获槽后仍复核Go状态，不允许迟到启动。
- 已发送的请求仍可能消耗费用；沿用允许迟到结算、不允许迟到发布的规则，不为本项强制中断HTTP而制造更多unknown。
- 页面候选不因取消或普通单页失败覆盖有效页面；成功结果继续持久保存。
- Node中的容量队列是本机短期调度状态，不是新的业务权威记录。Node退出后，现有Go租约/未知/显式继续机制负责恢复；未发送项按稳定身份重新准入，已发送未知项不自动重发。
- 队列项只保存必要身份和回调，不复制整套页面HTML、模板或截图；沿用原artifact引用，避免为了排队增加大量常驻内存。
- 共享额度和进度只使用鉴权后取得的owner，不接受用户自报身份；不展示其他客户数据。

## 7. 实施者提出的具体选择

以下为落实已确认边界而采用的实现选择：

| 选择 | 理由 |
|---|---|
| 新增Harness专用页工作位配置，默认3；固定流程原有DECK_CONCURRENCY默认2保留 | 现有参数同时作用两条链，分开配置避免未授权地同步提高旧链默认并发 |
| 页面共享池单独配置默认12；每Key活跃项目配置默认2，Brain全局继续5 | 分清整页、模型请求、项目、引擎四种容量，部署时可以分别验收调整 |
| Python只改Runner准入；模型容量池放Node的页面调用公共边界 | 符合单逻辑业务Node范围，避免另建Redis、消息服务或跨业务副本协调器 |
| Go增加可区分的在途预算等待原因和活动/等待登记 | 保持权威预算事务与准确有效时间，避免Node猜测余额或整体停表 |
| 内部等待使用已有通信和有界节奏的状态检查 | 不建设新的通知基础设施；同项目共享等待通知/检查，避免逐页高频读取完整快照 |
| 阶段等待作为子状态公开，保留现有phase与SSE通道 | 界面只补可观察进度，不另建任务状态机或新增用户配置表单 |
| 独立引擎算法、工作槽1和导出worker管理保持 | 已确认本机资源限制，避免把两个性能方向混成一次默认调整 |

具体新增配置名、内部状态字段名与测试命名由实施阶段按仓库风格确定；只校验实际需要的配置类型，不添加臆想兼容层或无用扩展点。

## 9. 必须验证的观察行为

- 单项目真正在模型阶段达到3的实际重叠；0/1/2页待办时不凭空增加请求。
- 页面池总量12；同owner大量排队不饿死其他owner，owner内部项目有推进机会。
- 同Key第3个Harness项目保持queued；别的Key能利用剩余Brain线程；等待用户/异常/取消/重复enqueue不漏占名额。
- 新旧在线调用共享池，大纲与总控不误入池；固定流程原有重试每次分别取还槽。
- 预算在途暂占不会误报永久不足，结算后可继续；实际不足/时间耗尽/unknown不会无限等待或继续收费。
- 等待额度期间取消/换epoch不会真正发送，已成功回执重放不拿槽、不扣费；unknown与并发reserve/send竞争有原子边界。
- 混合“某页等待、另一页在运行/校验/提交”计时正确；全等待不计，重启/继续无旧等待残留。
- Node/工具连接失败明确上报，项目/页面/原始资料及已确认约束不丢失；不新增自动付费恢复路径。
- 免费调度数据和真实模型/Chrome结果分开；真实消费必须新授权，未触发路径不宣称性能收益。

先沿用已有单测/假服务和核心检查，仅为这些真实并发边界增加窄测试；不新增独立测评框架。真实引擎2和多业务副本不作为本期已通过事项。

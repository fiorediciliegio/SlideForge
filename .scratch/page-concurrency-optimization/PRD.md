# 第五项：页面并发与多人容量调度

日期：2026-11-15。状态：已实施，免费调度验证和四进程健康预检完成；真实模型性能及完整多人吞吐尚未测评。

基线提交：`0b84b72c309f7ea191d488f0c9fcad5bdf6aa177`。

## 1. 目标

在页面质量、预算与恢复边界不变的前提下，小幅提高生成速度，并让多人同时生成时有明确的容量与公平性。分别测量生成、排队、校验和导出，不能把模型请求并发提高直接称为整体提速。

本项主要争取时间收益，不预设模型调用次数或费用下降。费用、首次通过率、返工、截断、失败及最终交付质量作为约束和观察指标。

## 2. 用户已确认的决策

| 决策 | 本期约定 |
|---|---|
| 每个Harness项目的整页处理并发 | 从2提高到3，覆盖初稿生成及已明确的批量修订；单页续改仍只有一页 |
| 页面模型请求共享上限 | 同一逻辑业务Node内12个，作为首轮验收起点，可通过服务端配置调整 |
| 共享额度范围 | 只计页面生成/修订的模型请求，不计Python总控与评审请求；不是供应商账号所有LLM调用的总上限 |
| 项目执行并发 | Brain仍为5个；每业务Key最多同时推进2个Harness项目，其余排队 |
| 公平性 | 按业务Key轮转，客户内部按项目推进；有空位立即使用，不给闲置客户预留容量，不抢占已发送请求 |
| 在线固定流程 | 同一Node内的固定流程HTTP、HTTP方式MCP及调用这些HTTP接口的WPS侧栏，也共享12个页面请求槽位 |
| 独立进程 | CLI、stdio方式MCP不纳入本期跨进程共享；多个业务Node副本的集中调度另期实施 |
| 引擎 | 本机默认仍为1；2是待验证档位，资源充足时再做固定HTML、零模型费用的对照验收 |
| 预算 | 仍使用已确认的任务上限；仅因在途预留暂不足则等待结算，真正不足再暂停 |
| 有效时间 | 纯等待容量不计入600秒；仍有模型、引擎或本地业务工作执行时按一段墙钟计一次 |
| 取消及未知 | 未发送请求停止派发；已发送请求允许结算，迟到结果不能发布；未知不自动重发 |
| 使用次数 | 本期不增加每日/月度生成次数限制，不增加会员套餐 |
| 第四项 | 上下文精简推迟，本期不实施 |
| 后续路线 | WPS、MCP、CLI未来统一调用同一套Agent Harness；本期保留固定流程，不提前迁移或删除 |

每Key的2个项目限制是真实取舍：一个客户提交多份作品时会排队，即使还有空闲Brain线程；每作品3个工作位仍可使用。等待用户确认大纲、等待用户补充、预算暂停和执行结束均释放项目名额，确认或继续后重新排队。已完成作品、仅打开界面和页面浏览不占名额。

这里的客户身份沿用业务Key的哈希，与当前鉴权、计费和作品归属一致，不等同稳定自然人账号。多个Key不会在本期自动合并为同一客户。

## 3. 已讨论的方案

### A：仅把整页并发2改为3

改动最小，但5个Harness项目的页面请求潜在峰值由10变为15，固定流程还有独立请求；无法处理跨项目争用与项目准入公平性。用户选择了同时管理共享容量的方案。

### B：整页并发3、页面请求共享12、项目准入5/每Key2

用户选择本方案。请求层控制总量，项目准入层避免同一客户先占满Brain线程。新增排队时长应可见；实现和验证范围较A大。

### C：同时把引擎并发默认提高到2

代码支持该配置，但现有真实引擎数据只验证了1；两个导出可能同时启动两套Node worker和Chrome。当前本机内存余量很小，用户同意暂不采用这个默认值，仅保留后续验收项。

## 4. 产品行为

- 队列未满时正常接收作品，容量忙时显示等待并自动继续，不要求重新点击生成。
- 全局或每Key名额不足，不应显示API Key错误、余额不足或任务失败。
- 沿用当前待执行项目队列的有界容量；队列确实满时明确返回繁忙，不丢弃已接收任务、不挤走正在运行任务。
- 界面区分“等待项目执行名额”“等待页面生成容量”“等待在途调用结算”和实际执行阶段，并显示本作品已完成页数。不给未经测量的预计完成时间或容易误导的绝对队列名次。
- 关闭网页仍按现有后台任务语义继续；只有明确取消才撤销未发送工作。
- 原来的模型费用上限、有效时间上限、每页最多两次返工、阻断页范围及交付闸门保持。
- 不在浏览器中暴露其他客户身份、作品或排队细节，也不把后端部署参数加入普通用户表单。

## 5. 本期不变更

不精简上下文、不改提示词/模板/思考配置、不调整总控8192及Agent单页16000上限，不更改转换算法，不扩大修订范围，不新增模型摘要、备用模型或自动付费重试。

固定流程仍保留原有生成和错误处理语义，本期只将其页面模型请求纳入共享调度，不把旧链路当作已获得Harness的预算与未知调用保障。引擎已有owner公平队列、固定快照、幂等导出和计费边界继续沿用。

## 6. 验收与解释边界

### 零模型费用

复用现有测试结构及假模型，验证1客户、5客户混合、10任务突发，以及同一Key超过2项目的准入；覆盖新旧在线路径争用、已完成回执复用、取消、未知、预算预留等待和恢复。

必须确认实际页面模型峰值不超过12、Harness整页工作位不超过3、活跃项目不超过5/每Key2；公平轮转不能被队首受限客户阻塞，有空闲容量时不人为等待。检查纯等待不计时、混合执行只计一次、未发送请求无模型费用、排队不生成重复调用ID。

### 性能与质量

真实模型测评继续沿用固定6类虚拟案例、每份6页、同模板/评分器和PPTX自动检查；只跑新版，读取已保存的`20261114-scope-16000`结果作为主要历史参考，不重跑旧版。新增显式并发3配置，不能修改冻结的并发2协议或伪造历史配置。

真实调用费用在执行前另行确认，本次设计确认不授权新的模型消费。零费用调度数据不能宣称为真实模型速度或质量提升。

报告同时列出生成及生成加导出的均值/中位数、实际模型调用与token、统一价格费用、截断率、首次程序通过率、初稿无需必要返工率、最终事实/章节/越界/交付/PPTX结果，以及多人排队P50/P95、各客户完成情况、实际并发与资源采样。只测单用户不能宣布多人吞吐验收通过。

不预设必然提速；如果单用户更快但多人明显退化，应报告并调整容量后判断，不把相对较差的一轮恢复称为已证明的普遍优化。历史单次样本不作单变量因果结论。

引擎2需另做固定HTML、1/2对照，确认真实并行、双导出与检查/导出混合、取消隔离、文件归属、完整四进程及Chrome资源占用；没有通过前不改变本机默认1，也不阻塞页面并发3的调度逻辑验收。
